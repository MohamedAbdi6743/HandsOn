# HandsOn – Architecture Proposal

HandsOn is a volunteer shift scheduler for a small nonprofit. Coordinators post events
split into shifts. Volunteers sign up, cancel, or join a waitlist. Coordinators record
attendance and see how many hours each volunteer has worked.

This document is the plan we agree on before writing code.

---

## 0. Scope (what's in, what's out)

**In version 1**

- One organization per installation.
- Two roles: `COORDINATOR` and `VOLUNTEER`.
- Events with one or more shifts. Each shift has a start time, end time and capacity.
- Sign-up rules:
  1. A volunteer can't sign up for the same shift twice.
  2. A volunteer can't hold two shifts that overlap in time.
  3. If a shift is full, the volunteer joins the waitlist instead.
  4. A volunteer can't cancel within 12 hours of the shift start (configurable).
  5. When a confirmed volunteer cancels, the first person on the waitlist is promoted automatically.
  6. You can't sign up for a shift that has already started.
- Coordinators mark attendance (attended / no-show) after a shift starts.
- An hours report per volunteer over a date range.

**Out of version 1 (possible future work)**

Email reminders, recurring shifts, multiple organizations, CSV export, deployment to
the internet.

## 1. High-level architecture

```
 ┌──────────────────────────────────────────────┐
 │  Browser                                     │
 │  HTML pages + CSS + compiled TypeScript      │
 │  (events.html, event.html, my-shifts.html…)  │
 └───────────────┬──────────────────────────────┘
                 │  HTTP requests with JSON bodies
                 │  e.g. POST /api/shifts/7/signups
                 │  (session cookie + CSRF header attached)
                 ▼
 ┌──────────────────────────────────────────────┐
 │  Spring Boot application (one process)       │
 │                                              │
 │  Spring Security filter                      │
 │    "Who is this? Are they allowed?"          │
 │                 │                            │
 │                 ▼                            │
 │  Controllers   (HTTP in / JSON out)          │
 │                 │  DTOs                      │
 │                 ▼                            │
 │  Services      (business rules,              │
 │                 transactions)                │
 │                 │  Entities                  │
 │                 ▼                            │
 │  Repositories  (Spring Data JPA)             │
 │                 │                            │
 │  Also serves the static frontend files       │
 └───────────────┬──────────────────────────────┘
                 │  SQL over JDBC (generated by Hibernate,
                 │  always with bound parameters)
                 ▼
 ┌──────────────────────────────────────────────┐
 │  PostgreSQL                                  │
 │  tables: app_user, event, shift, signup      │
 │  schema created by Flyway migrations         │
 └──────────────────────────────────────────────┘
```

**In plain English**

- **Browser / frontend:** the pages the user sees. TypeScript code in each page calls the
  backend with `fetch()` and draws the results on the screen.
- **HTTP requests:** the browser and server talk over HTTP. The request URL says *what*
  (`/api/events/3`), the method says *what to do* (`GET` = read, `POST` = create, and so on),
  and the body carries JSON data.
- **REST API:** the set of URLs the backend exposes. It's the backend's "menu".
- **Spring Security:** runs before any controller. It checks the session cookie to find out
  who the user is and blocks requests they aren't allowed to make.
- **Controllers:** receive the HTTP request, check the input is well-formed, call a service,
  and turn the result into an HTTP response.
- **Services:** where the rules live ("is this shift full?"). This is the heart of the app.
- **Repositories:** the only code that talks to the database. Spring Data writes most of
  the SQL for us.
- **PostgreSQL:** stores the data permanently and enforces constraints as a last line of
  defense.

**Why one application and not microservices?** One small team and one database. Splitting
into services would add network calls, deployment work and failure points without solving
any problem we have. A single well-organized app (a "modular monolith") is what most
companies start with.

## 2. Backend architecture

### 2.1 The layers

**Controller → Service → Repository → PostgreSQL**

| Layer | Responsibility | Belongs here | Does NOT belong here |
|---|---|---|---|
| **Controller** | Translate HTTP ↔ Java | URL mappings, `@Valid` request DTOs, choosing the status code, reading the logged-in user | Business rules, SQL, `if (shift is full)` logic |
| **Service** | Business rules and transactions | Sign-up rules, waitlist promotion, `@Transactional`, logging important actions | HTTP details (status codes, headers), SQL strings |
| **Repository** | Load and save data | Spring Data interfaces, custom queries | Rules, HTTP |
| **Database** | Store data, enforce integrity | Foreign keys, unique and check constraints, indexes | Application logic |

**How they talk:** a controller calls a service method. The service calls one or more
repositories. Each layer only calls the layer directly below it.

**Why separate them?**

- **Testing:** we can unit-test `SignupService` rules with fake repositories (Mockito),
  without starting a web server or a database.
- **Change:** if we later add a mobile app or a scheduled job, it calls the same services.
  The rules aren't trapped inside HTTP code.
- **Reading:** a new developer knows where to look. A rule is in a service. A URL is in a
  controller.

**What if a layer didn't exist?**

- *No service layer:* rules end up copied across controllers, and transactions get messy.
  Testing a rule would mean sending fake HTTP requests.
- *No repository layer:* SQL is scattered everywhere, which makes mistakes (and SQL
  injection) more likely.
- *No controller layer:* services would be full of HTTP details and could only be used
  from the web.

**Why no `SignupService` interface + `SignupServiceImpl`?** With only one implementation,
the interface adds a file and no value. Mockito can mock concrete classes. We'd add an
interface only if a real second implementation appeared.

### 2.2 Concepts we'll use (short versions; each is explained fully when we build it)

- **Entity:** a Java class mapped to a table (`Shift` ↔ `shift`). Hibernate turns objects
  into rows and back.
- **DTO (Data Transfer Object):** a simple class describing exactly what the API sends or
  receives. We use Java `record`s. *Why not return entities directly?* Entities hold
  things the client shouldn't see (password hash), can cause infinite JSON loops
  (event → shifts → event…), and tie the API shape to the table shape.
- **Dependency injection:** Spring creates objects and passes in what each one needs through
  the constructor. `SignupService` asks for a `SignupRepository` and Spring supplies it. In
  tests we pass a fake one instead.
- **Validation:** annotations such as `@NotBlank` and `@Positive` on request DTOs. Spring
  rejects bad input with a `400` before our code runs.
- **Centralized exception handling:** one `@RestControllerAdvice` class turns exceptions
  into consistent JSON errors, so no controller needs its own `try/catch`.
- **Transactions:** `@Transactional` means "all of these database changes succeed together,
  or none of them happen". Cancelling a sign-up and promoting the next person must happen
  together.
- **`Clock` injection:** services ask a `Clock` bean for "now" instead of calling
  `LocalDateTime.now()` directly. Tests can then freeze time to check rules like "can't
  cancel within 12 hours".

### 2.3 Package layout (organized by layer)

```
com.handson
├── HandsOnApplication.java
├── config/        SecurityConfig, ClockConfig
├── controller/    AuthController, EventController, ShiftController,
│                  SignupController, ReportController
├── service/       UserService, EventService, ShiftService,
│                  SignupService, ReportService
├── repository/    UserRepository, EventRepository, ShiftRepository,
│                  SignupRepository
├── entity/        AppUser, Event, Shift, Signup, Role, SignupStatus
├── dto/           request and response records
└── exception/     GlobalExceptionHandler, NotFoundException,
                   BusinessRuleException, ErrorResponse
```

*Alternative:* package by feature (`event/`, `signup/`, …). That scales better in big
codebases. For about 30 classes, packaging by layer matches the diagram above and is
easier to follow at first.

### 2.4 The trickiest part: two people grab the last spot

Two volunteers click "Sign up" on a shift with 1 spot left at the same moment. Without
care, both requests count "4 of 5 taken", both insert a row, and the shift ends up with
6 people.

**Chosen approach:** inside one transaction, load the shift **with a row lock**
(`SELECT … FOR UPDATE`, via Spring Data's `@Lock(PESSIMISTIC_WRITE)`). The second request
waits until the first one finishes. It then counts again, sees the shift is full, and is
put on the waitlist.

| Option | Why / why not |
|---|---|
| **Pessimistic row lock (chosen)** | Easy to explain: "lock the shift while we count." Brief waits only happen on the same shift, which is fine at this scale. |
| Optimistic locking (`@Version`) | The loser gets an error and must retry. More code for the same result. |
| Do nothing | Overbooking. Not acceptable. |

A database `UNIQUE (shift_id, user_id)` constraint also blocks the same person signing up
twice, even if two requests arrive at once.

## 3. Frontend architecture

### 3.1 Approach

A **multi-page app**: one HTML file per screen, each with a small TypeScript file. No
framework and no client-side router. The browser handles navigation like a normal
website.

Spring Boot serves the frontend files itself, so the frontend and API share one address
(`http://localhost:8080`). That means **no CORS setup** is needed, and session cookies
just work.

### 3.2 Folders

```
frontend/
├── package.json        (only one dev dependency: typescript)
├── tsconfig.json       (compiles src/*.ts → backend static/js/)
└── src/
    ├── api.ts          one place for fetch(), JSON, CSRF header, error handling
    ├── auth.ts         get current user, redirect to login if needed
    ├── dom.ts          small helpers: show message, set loading, format dates
    ├── types.ts        TypeScript types matching the API DTOs
    ├── login.ts
    ├── register.ts
    ├── events.ts       list of upcoming events
    ├── event.ts        event detail: shifts, sign-up/cancel buttons, roster (coordinator)
    ├── my-shifts.ts    my sign-ups and total hours
    ├── manage-event.ts coordinator: create/edit event and its shifts
    └── reports.ts      coordinator: hours report

src/main/resources/static/
├── *.html              one per screen
├── css/main.css        variables, layout, components
└── js/                 compiled output (ignored by Git)
```

### 3.3 How a user action flows

Example: clicking **Sign up** on `event.html`.

1. The click handler in `event.ts` disables the button and shows "Signing up…".
2. It calls `api.post('/api/shifts/7/signups')` in `api.ts`, which adds the CSRF header
   and sends the request.
3. If the response is `201`, it shows "You're confirmed" (or "You're #2 on the waitlist")
   and reloads the shift list.
4. If the response is `409`, it shows the server's message (for example "This overlaps
   with your Food Drive shift").
5. If the response is `401`, it redirects to the login page.
6. Finally, it re-enables the button.

Every page handles **loading, empty, error and success** states the same way, using
helpers in `dom.ts`.

### 3.4 Safety and accessibility

- User text is always inserted with `textContent`, never `innerHTML`. A volunteer named
  `<script>…` shows up as plain text and doesn't run (this prevents XSS).
- We use real `<button>`, `<label>` and `<form>` elements, and messages appear in an
  `aria-live` region so screen readers announce them.
- The CSS is mobile-first and uses flexbox/grid, so pages work on a phone.

### 3.5 Build

`npm run build` runs the TypeScript compiler (`tsc`), and `npm run watch` recompiles on
save. Node is used **only** to compile TypeScript. There's no bundler and no framework.

## 4. Database design

### 4.1 Entity-relationship diagram

```
 app_user                     event
 ─────────────────            ──────────────────
 PK id                        PK id
    email (unique)               title
    password_hash                description
    full_name                    location
    role                      FK created_by → app_user.id
    created_at                   created_at
        │ 1                          │ 1
        │                            │
        │ many                       │ many
        ▼                            ▼
 signup                       shift
 ─────────────────            ──────────────────
 PK id                        PK id
 FK user_id  → app_user.id    FK event_id → event.id
 FK shift_id → shift.id ◄──── many │ 1   title
    status                       start_time
    created_at                   end_time
    updated_at                   capacity
 UNIQUE (shift_id, user_id)
```

- One **event** has many **shifts**.
- One **user** has many **signups**. One **shift** has many **signups**.
- So users ↔ shifts is a **many-to-many** relationship, and `signup` is the table in the
  middle. It's a full table, not a hidden join table, because it carries its own data
  (status and timestamps).

### 4.2 Tables

**`app_user`**: everyone who can log in. It's called `app_user` because `user` is a
reserved word in PostgreSQL.

| Column | Type | Rules |
|---|---|---|
| id | `BIGINT GENERATED ALWAYS AS IDENTITY` | primary key |
| email | `VARCHAR(255)` | not null, **unique** (stored lowercase) |
| password_hash | `VARCHAR(100)` | not null, BCrypt hash, never the raw password |
| full_name | `VARCHAR(100)` | not null |
| role | `VARCHAR(20)` | not null, `CHECK (role IN ('COORDINATOR','VOLUNTEER'))` |
| created_at | `TIMESTAMP` | not null, default now |

*Why no separate `volunteer` table?* A volunteer is a user with a role. Two tables would
duplicate name and email for no gain.

**`event`**

| Column | Type | Rules |
|---|---|---|
| id | `BIGINT` identity | primary key |
| title | `VARCHAR(120)` | not null |
| description | `TEXT` | nullable |
| location | `VARCHAR(200)` | not null |
| created_by | `BIGINT` | FK → `app_user(id)`, not null |
| created_at | `TIMESTAMP` | not null, default now |

**`shift`**

| Column | Type | Rules |
|---|---|---|
| id | `BIGINT` identity | primary key |
| event_id | `BIGINT` | FK → `event(id)` `ON DELETE CASCADE`, not null |
| title | `VARCHAR(80)` | not null (e.g. "Setup crew") |
| start_time | `TIMESTAMP` | not null |
| end_time | `TIMESTAMP` | not null, `CHECK (end_time > start_time)` |
| capacity | `INTEGER` | not null, `CHECK (capacity > 0)` |

Indexes: `(event_id)` and `(start_time)`.

**`signup`**

| Column | Type | Rules |
|---|---|---|
| id | `BIGINT` identity | primary key |
| shift_id | `BIGINT` | FK → `shift(id)`, not null |
| user_id | `BIGINT` | FK → `app_user(id)`, not null |
| status | `VARCHAR(20)` | `CHECK (status IN ('CONFIRMED','WAITLISTED','CANCELLED','ATTENDED','NO_SHOW'))` |
| created_at | `TIMESTAMP` | not null. This is also the waitlist order (first come, first served). |
| updated_at | `TIMESTAMP` | not null |

Constraint: `UNIQUE (shift_id, user_id)`. If someone cancels and later signs up again, we
**reactivate their existing row** instead of inserting a new one.
Indexes: `(user_id)` (for "my shifts" and overlap checks) and `(shift_id, status)` (for
counting confirmed people).

**Signup status lifecycle**

```
            sign up (spot free)            shift starts, coordinator marks
  (none) ─────────────────────► CONFIRMED ─────────────► ATTENDED / NO_SHOW
     │                            ▲    │
     │ sign up (full)   promoted  │    │ cancel (>12h before)
     ▼                            │    ▼
  WAITLISTED ─────────────────────┘  CANCELLED
     │ cancel (any time)
     └────────────────────────────►  CANCELLED
```

### 4.3 Times and time zones

We store `TIMESTAMP` (no time zone) and use Java `LocalDateTime`. This means "the
organization's local time". One organization in one city makes this the simplest correct
choice. *Growth path:* across several time zones we'd switch to `TIMESTAMPTZ` + `Instant`
and convert in the browser.

### 4.4 Sample data

```
app_user
 1 | coordinator@handson.test | Dana Lee   | COORDINATOR
 2 | sam@example.com          | Sam Ortiz  | VOLUNTEER
 3 | priya@example.com        | Priya Shah | VOLUNTEER

event
 1 | Saturday Food Drive | Community Center, Hall B | created_by 1

shift
 1 | event 1 | Setup crew     | 2026-12-05 08:00 → 10:00 | capacity 2
 2 | event 1 | Sorting tables | 2026-12-05 10:00 → 13:00 | capacity 5

signup
 1 | shift 1 | user 2 | CONFIRMED
 2 | shift 1 | user 3 | CONFIRMED
 3 | shift 2 | user 3 | WAITLISTED   (example only)
```

### 4.5 Migrations

Schema changes live in versioned SQL files (`V1__create_tables.sql`, `V2__…`) that
**Flyway** applies on startup. Hibernate is set to `ddl-auto: validate`: it checks the
tables match the entities but never changes them itself.
*Why:* every database (yours, a teammate's, production) ends up with exactly the same
schema, and changes are reviewed like any other code.

## 5. API design

All URLs start with `/api`. Request and response bodies are JSON.
Who can call each endpoint: **Public**, **Any** (any logged-in user), **Vol** (volunteer)
or **Coord** (coordinator).

### 5.1 Error format (same for every error)

```json
{
  "status": 409,
  "error": "Conflict",
  "message": "This shift overlaps with 'Setup crew' (Dec 5, 08:00–10:00).",
  "fieldErrors": {},
  "timestamp": "2026-12-01T14:03:22"
}
```

For validation errors (`400`), `fieldErrors` lists each problem, e.g.
`{"capacity": "must be greater than 0"}`.

### 5.2 Status codes we use

| Code | Meaning in HandsOn |
|---|---|
| 200 OK | Read or update succeeded |
| 201 Created | Something new was created (also returns its data) |
| 204 No Content | Succeeded, nothing to return (delete, logout) |
| 400 Bad Request | Input is malformed or fails validation |
| 401 Unauthorized | Not logged in |
| 403 Forbidden | Logged in, but not allowed (volunteer calling a coordinator endpoint) |
| 404 Not Found | The ID doesn't exist |
| 409 Conflict | Valid input, but it breaks a business rule (overlap, too late to cancel, duplicate email) |

### 5.3 Endpoints

**Auth**

| Method | URL | Who | Purpose | Success | Errors |
|---|---|---|---|---|---|
| POST | `/api/auth/register` | Public | Create a volunteer account | 201 | 400, 409 email taken |
| POST | `/api/auth/login` | Public | Log in (starts a session) | 200 | 401 |
| POST | `/api/auth/logout` | Any | Log out | 204 | – |
| GET | `/api/auth/me` | Any | Who am I? | 200 | 401 |

```http
POST /api/auth/register
{ "fullName": "Sam Ortiz", "email": "sam@example.com", "password": "correct-horse-42" }

201 Created
{ "id": 2, "fullName": "Sam Ortiz", "email": "sam@example.com", "role": "VOLUNTEER" }
```

Validation: name 1–100 characters, valid email, password at least 10 characters.

**Events**

| Method | URL | Who | Purpose | Success | Errors |
|---|---|---|---|---|---|
| GET | `/api/events` | Any | Upcoming events with spot counts | 200 | – |
| GET | `/api/events/{id}` | Any | Event with its shifts | 200 | 404 |
| POST | `/api/events` | Coord | Create an event | 201 | 400 |
| PUT | `/api/events/{id}` | Coord | Edit an event | 200 | 400, 404 |
| DELETE | `/api/events/{id}` | Coord | Delete an event | 204 | 404, 409 has sign-ups |

```http
GET /api/events/1

200 OK
{
  "id": 1, "title": "Saturday Food Drive", "location": "Community Center, Hall B",
  "description": "Sorting donated food for 40 families.",
  "shifts": [
    { "id": 1, "title": "Setup crew",
      "startTime": "2026-12-05T08:00", "endTime": "2026-12-05T10:00",
      "capacity": 2, "confirmedCount": 2, "waitlistCount": 1,
      "mySignup": { "id": 9, "status": "WAITLISTED", "waitlistPosition": 1 } }
  ]
}
```

**Shifts**

| Method | URL | Who | Purpose | Success | Errors |
|---|---|---|---|---|---|
| POST | `/api/events/{eventId}/shifts` | Coord | Add a shift | 201 | 400, 404 |
| PUT | `/api/shifts/{id}` | Coord | Edit a shift | 200 | 400, 404, 409 capacity below confirmed count |
| DELETE | `/api/shifts/{id}` | Coord | Remove a shift | 204 | 404, 409 has sign-ups |

Validation: title required, end after start, capacity 1–500.

**Sign-ups**

| Method | URL | Who | Purpose | Success | Errors |
|---|---|---|---|---|---|
| POST | `/api/shifts/{shiftId}/signups` | Vol | Sign up (confirmed or waitlisted) | 201 | 404, 409 duplicate / overlap / already started |
| POST | `/api/signups/{id}/cancel` | Vol (own) | Cancel; promotes the next waitlisted person | 200 | 403, 404, 409 too late |
| GET | `/api/me/signups` | Vol | My upcoming and past sign-ups | 200 | – |
| GET | `/api/shifts/{id}/signups` | Coord | Shift roster and waitlist | 200 | 404 |
| PUT | `/api/signups/{id}/attendance` | Coord | Mark attended / no-show | 200 | 404, 409 shift not started or not confirmed |

```http
POST /api/shifts/1/signups        (no body; the volunteer is the logged-in user)

201 Created
{ "id": 9, "shiftId": 1, "status": "WAITLISTED", "waitlistPosition": 1 }
```

*Why is cancel a `POST /cancel` and not `DELETE`?* We keep the row as history
(`CANCELLED`). `DELETE` would suggest the record disappears.

**Reports**

| Method | URL | Who | Purpose | Success | Errors |
|---|---|---|---|---|---|
| GET | `/api/reports/volunteer-hours?from=2026-01-01&to=2026-12-31` | Coord | Hours per volunteer | 200 | 400 bad dates |
| GET | `/api/me/hours` | Vol | My total hours | 200 | – |

```http
200 OK
[
  { "userId": 3, "fullName": "Priya Shah", "shiftsAttended": 6, "totalHours": 17.5 },
  { "userId": 2, "fullName": "Sam Ortiz",  "shiftsAttended": 4, "totalHours": 9.0 }
]
```

Hours are counted from `ATTENDED` sign-ups only, using one SQL query with `SUM` and
`GROUP BY`.

## 6. Design decisions

### D1. Login: server sessions, not JWT
1. **Problem:** we need to know who is making each request.
2. **Choice:** Spring Security with a server-side session and an `HttpOnly` cookie.
3. **Why:** the frontend and backend share one address, so cookies work automatically.
   JavaScript can't read an `HttpOnly` cookie, which makes it harder to steal.
4. **Alternatives:** JWT tokens stored in the browser.
5. **Trade-offs:** sessions live in server memory, so restarting the server logs everyone
   out. Fine for us. JWTs need token storage, expiry and refresh logic, which is more code
   for no benefit here.
6. **If it grew:** store sessions in the database (Spring Session JDBC) so several servers
   can share them.

### D2. CSRF protection stays on
1. **Problem:** with cookies, another website could trick a logged-in browser into sending
   a request (cross-site request forgery).
2. **Choice:** Spring Security's CSRF tokens. The server sets an `XSRF-TOKEN` cookie, and
   `api.ts` copies it into an `X-XSRF-TOKEN` header on every change request.
3. **Why:** many tutorials just call `csrf().disable()`. Keeping it on, and being able to
   explain why, is a good signal in an interview.
4. **Alternative:** disabling CSRF (only safe with token-based login).
5. **Trade-off:** a few extra lines in `api.ts`.

### D3. Passwords
BCrypt hashing via Spring Security's `PasswordEncoder`. We never store or log raw
passwords. *Alternative:* plain SHA-256. That's too fast to compute, which makes
brute-forcing stolen hashes easy.

### D4. The first coordinator account
Public registration only creates volunteers. The first coordinator is created at startup
**from environment variables** (`HANDSON_ADMIN_EMAIL`, `HANDSON_ADMIN_PASSWORD`) if it
doesn't exist yet. *Alternative:* hard-coding a coordinator in a migration. That would put
a password (or hash) in Git.

### D5. Configuration and secrets
`application.yml` reads `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` and the admin variables
from the environment. No real secrets are committed. Profiles: `dev` (readable logs,
sample data) and `test` (used by automated tests). A `.env.example` lists every variable
without real values.

### D6. Business rule violations → `409`, one exception type
Services throw `BusinessRuleException("This shift overlaps…")`, and the global handler
turns it into a `409` with that message. *Alternative:* a custom exception class per rule.
That's more files for the same behavior. One exception type plus a clear message is
enough.

### D7. Waitlist order by `created_at`
No separate "position" column. Position = how many waitlisted rows on that shift were
created earlier, plus 1. *Trade-off:* the position is calculated each time. That's cheap
at this size, and it can never get out of sync.

### D8. Frontend: plain TypeScript, multi-page
No framework, as requested. A multi-page app avoids writing our own router or state
management. *Trade-off:* some repeated header markup in the HTML files. That's acceptable,
and we keep it small. *If it grew:* a framework like React would start to pay off once
there are many shared, interactive components.

### D9. Local database: PostgreSQL in Docker *(needs your approval)*
PostgreSQL isn't installed on your machine, but Docker is. One small `compose.yaml` file
starts PostgreSQL with `docker compose up -d`, and anyone cloning the repo gets the same
database version.
*Alternative:* install PostgreSQL directly on Windows. That works too, but each reviewer
has to install it themselves.

### D10. Integration tests against real PostgreSQL *(needs your approval)*
**Testcontainers** starts a throwaway PostgreSQL in Docker for the tests. That means the
real database, real constraints and real row locks. The "last spot" test can only be
trusted on real PostgreSQL.
*Alternative:* H2 (an in-memory database). It's faster to set up, but it behaves
differently from PostgreSQL, so passing tests could hide real bugs.

### D11. Build tool
Maven Wrapper (`mvnw`). It downloads the correct Maven version automatically, so you
don't need to install Maven, and neither does anyone cloning the repo.

| typescript (npm, dev only) | Compiling TypeScript *(approval)* |

Nothing else: no Lombok, no MapStruct, no frontend libraries. We map DTOs by hand
because it's easy to read.

## 8. Milestone plan

Each milestone is built, tested, explained and committed before the next one starts.

1. **Project setup:** Spring Boot skeleton, PostgreSQL in Docker, Flyway `V1` schema,
   app starts and connects.
2. **Events & shifts API:** entities, repositories, services, controllers, validation,
   global error handler, tests.
3. **Users & security:** registration, login/logout, roles, CSRF, first coordinator
   account, security tests.
4. **Sign-up rules:** capacity, duplicates, overlap, waitlist, cancel cutoff, promotion,
   row locking. Unit tests for every rule, plus a concurrency test.
5. **Attendance & reports:** marking attendance, hours query, report endpoints.
6. **Frontend part 1:** `api.ts`, login/register, events list, event detail with
   sign-up/cancel.
7. **Frontend part 2:** my shifts, coordinator manage-event page, roster, reports page.
8. **Hardening & docs:** end-to-end manual test pass, security checks, README with
   screenshots, final review.
